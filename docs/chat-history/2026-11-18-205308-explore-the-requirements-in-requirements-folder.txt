  ⎿  9 findings, most severe first:

     1. services.py:98: The capacity check is a count followed by a separate insert, with no lock or atomic guard, so concurrent registrations can overbook an event.

        Failure scenario: An event has max_capacity=1 and 0 registrations. Two requests with different emails arrive concurrently. Both read count=0 and pass the check, both insert, and the event ends up with 2 of 1 seats. The unique constraint only covers (event_id, email), so nothing stops this. Fix by locking the event row with select(...).with_for_update() in get_event for this path, or by using a conditional insert.
     2. services.py:53: update_event reads the registration count and then writes max_capacity without locking the event row, so it races with create_registration.

        Failure scenario: An event has capacity 10 and 9 registrations. A PUT sets capacity to 9 and passes the check (9 >= 9). Meanwhile a registration passes its own check (9 < 10) and commits. The event ends up with capacity 9 and 10 registrations, which violates the invariant the update check is meant to protect.
     3. services.py:107: Any IntegrityError on commit is reported as a duplicate-email conflict. It could also be an FK violation, such as the event being deleted concurrently.

        Failure scenario: The event is deleted between get_event and commit. The insert fails the events.id foreign key, and the client gets 409 'already registered' instead of 404. The raise inside the except also lacks from None or from exc, so the original error is chained confusingly. Inspect the constraint name or re-check the event before choosing the message.
     4. db.py:17: The default DATABASE_URL falls back to hard-coded postgres:postgres credentials on localhost when the env var is missing.

        Failure scenario: A deployment without DATABASE_URL silently tries default superuser credentials, or connects to an unintended local DB. It should fail fast with a clear error instead.
     5. schemas.py:20: Validation is inconsistent. description has no max length or blank handling, and date accepts past dates, with no check that a new event is in the future. _reject_blank also runs after min_length, so the min_length is redundant.

        Failure scenario: A client posts a multi-megabyte description, which is stored in a Text column unchecked. A client creates an event dated 1900-01-01 and it is accepted. A whitespace-only description is stored as-is.
     6. schemas.py:52: EventResponse inherits from EventBase, so output serialization re-runs input validators (strip, min_length, gt=0).

        Failure scenario: A row inserted outside the API, such as a title with only spaces or max_capacity=0, makes every GET /events return a 500 ResponseValidationError. One bad row breaks the whole list endpoint. A separate response model without the input constraints would avoid this.
     7. services.py:88: The email is lowercased in application code, while the unique constraint and the existing-row lookup rely on lower() in the query. The DB constraint itself is case-sensitive.

        Failure scenario: Rows written by another path, or before this logic, with mixed-case emails are not covered by uq_event_attendee. Only the application-level func.lower check catches them, and it is not atomic. A functional unique index on lower(attendee_email) would enforce the rule in the DB.
     8. main.py:23: Schema is managed with create_all() at startup, with no migrations. Existing tables are never altered.

        Failure scenario: After a model change such as a new column or constraint, create_all skips the existing table. The deployed DB silently diverges from the models, which causes runtime SQL errors or a missing uq_event_attendee constraint.
     9. models.py:37: ondelete='CASCADE' is declared on the FK but not paired with passive_deletes on the relationship. The ORM therefore loads every registration into memory to delete them one by one.

        Failure scenario: Deleting an event with thousands of registrations issues a SELECT plus N individual DELETEs. Setting passive_deletes=True would let the DB cascade in one statement.
